# Cortex + JupyterHub/JupyterLab integration and security boundary

## Decision

Cortex will use the real Jupyter ecosystem as an execution plane rather than reimplementing a notebook kernel. Cortex remains the authenticated control plane: it owns organizations, workspaces, projects, authorization, quotas, provenance, secrets references and lifecycle metadata. JupyterHub/Jupyter Server/JupyterLab provide the execution plane through provider adapters.

The initial browser shell is a Cortex control-plane surface. It must not claim that a kernel, terminal, notebook execution or runtime exists until a real adapter reports that capability.

## Official architecture to integrate

JupyterHub is composed of a Hub, configurable HTTP proxy, authenticators and multiple single-user Jupyter notebook servers managed by spawners. Cortex maps onto that architecture as follows:

| Jupyter subsystem | Cortex responsibility | Boundary |
|---|---|---|
| Authenticator | Existing Formbricks/Better Auth session and workspace authorization | Cortex issues only scoped, short-lived runtime credentials |
| Hub | Cortex runtime service or JupyterHub deployment | Cortex requests lifecycle operations; it does not bypass Hub state |
| Proxy | JupyterHub proxy or a provider-specific ingress | No direct exposure of single-user servers |
| Spawner | Runtime adapter backed by local/container/Kubernetes/cloud provider | Enforces CPU, memory, GPU, TTL and network policy |
| Single-user server | User's Jupyter Server/JupyterLab instance | Isolated per user/project runtime |
| JupyterLab | Real notebook UI when runtime is connected | Embedded or proxied; no counterfeit kernel UI |

## Security controls before execution is enabled

### Identity and tenancy

Every runtime request must carry a verified Cortex user, organization, workspace and project scope. A runtime identifier alone is never sufficient authorization. The adapter must re-check ownership and membership before start, proxy, stop, file access or artifact retrieval.

### Runtime isolation

A production spawner must use a separate runtime per user/project, a non-root user, a read-only base image where practical, a dedicated writable workspace volume, CPU/memory/process limits, a maximum lifetime and explicit cleanup. Docker and Kubernetes adapters must deny privileged containers, host networking, host PID, host mounts and arbitrary device access by default.

### Network policy

Outbound network access is disabled by default for untrusted notebook code. If enabled for a provider or project, it must be an explicit capability with an allowlist, egress audit trail and quota. The Cortex control plane is never reachable through unrestricted runtime credentials.

### Credentials and secrets

Provider tokens, Git tokens, Hugging Face tokens and cloud credentials are stored as secret references, never notebook source or ordinary database plaintext. Runtime credentials are short-lived, scoped to one project and revoked when a runtime stops. Logs and notebook outputs must pass redaction before persistence or display.

### Proxy and browser security

Single-user servers are reachable only through the authenticated proxy path. Runtime URLs must be unguessable and validated against the authorized project before proxying. Cookies must use secure, HTTP-only and appropriate SameSite settings. Cross-origin requests require an explicit origin policy. WebSocket upgrades must preserve the same authorization context as HTTP requests.

### Files and artifacts

Notebook paths are normalized and rejected if they escape the project root. Object storage keys are generated by Cortex and are not accepted as arbitrary user paths. Downloads use short-lived signed URLs and project-scoped authorization. Artifacts record checksum, source revision, runtime image and creator.

### Quotas and lifecycle

Every runtime has a quota class, resource request, maximum TTL and cleanup policy. Starting a runtime is rejected when the workspace or organization quota is exhausted. Stop and cleanup operations are idempotent. Orphan detection runs independently of the browser session.

### Auditability

Record runtime requested, provisioned, started, proxied, stopped, failed and destroyed events with actor, workspace, project, provider, resource request, correlation ID and timestamps. Never log tokens, kernel connection files or raw secrets.

## Adapter contract requirements

A Jupyter adapter is production-ready only if it implements:

- capability discovery;
- tenant-scoped runtime start/stop/status;
- authenticated proxy URL creation;
- websocket authorization;
- resource and TTL enforcement;
- log streaming with redaction;
- artifact and notebook path handling;
- cancellation and cleanup;
- health checks and failure-state reporting.

A provider adapter must return `unavailable` rather than a successful-looking placeholder when JupyterHub/Jupyter Server is not configured.

## Rollout sequence

1. Keep the current Cortex shell in explicit control-plane mode.
2. Add a runtime adapter interface with capability discovery and security-state checks.
3. Add a local development Jupyter Server adapter with no production claims.
4. Add a container adapter with non-root and resource-limit enforcement.
5. Add JupyterHub integration for multi-user spawning and proxying.
6. Add Kubernetes/cloud providers only after quota, secrets, audit and cleanup tests pass.
7. Replace the shell's unavailable state with the real JupyterLab surface only when the adapter health check succeeds.
